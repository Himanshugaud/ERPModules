Initial date: 2026-10-18. Follow-up: 2026-10-24. Status: local hardening and release-gate configuration updated; full audit and release approval **not complete**.

Audit testing made no production API calls or production data mutations, credential rotations, or application deployments. HTTP authorization across every endpoint, realistic database concurrency, production recovery controls, and representative load remain release gates.

## Architecture and Trust Boundaries

- Frontend: React 18.3.1, TypeScript 5.5.4, Vite 5, React Router 6. Express 4 serves the static SPA. ExcelJS is dynamically loaded for requirement-sheet import/export.
- Active API: Azure Functions isolated worker, .NET 9, ASP.NET Core integration. The solution contains Api, Application, Domain, Infrastructure, and Shared layers. FluentValidation validates typed request DTOs; System.Text.Json serializes envelopes.
- Persistence: EF Core 9 SQL Server provider, handwritten entity mappings, SQL schema scripts rather than EF migrations. Six SQL schema files contain 69 CREATE TABLE declarations in total; these are source declarations, not a live database table count. Runtime schema equivalence was not checked.
- Identity: local password login with existing PBKDF2 password handling and self-issued HS256 JWTs. This is not end-user Microsoft Entra token validation. DefaultAzureCredential is used separately for Azure SQL/Blob resource authentication.
- Authorization: application permission/role guards, signed organization claims, scoped ITenantContext, and explicit repository organization predicates. Azure Functions host-level Anonymous declarations deliberately leave application authentication responsible for protection.
- Inventory: append-only movement ledger, stock-balance projection, weighted-average costing, transactional services, and SQL Server rowversion on selected aggregates. Existing UnitOfWork maps EF concurrency exceptions to application conflicts/HTTP 409.
- Attachments: Azure Blob SDK, managed-identity-capable credentials, organization/project-derived paths, database document metadata, soft deletion, maximum file size, and download disposition/nosniff handling.
- Telemetry: Application Insights registration, exception middleware, audit rows, and outbox rows. The event publisher is a logging stub; durable external delivery was not verified.
- Legacy root service: TypeScript Azure Functions, mssql connection pool, health and function-key-protected database diagnostics. It remains a separate dependency and reliability surface.
- Hosting: source supports Azure Functions and an Azure App Service static frontend. No tracked GitHub Actions/Azure Pipelines definitions, Bicep, Terraform, Dockerfile, or Compose configuration were found. Actual cloud settings, RBAC, network rules, CORS, TLS policy, backups, and alerts were not queried.

Local configuration was parsed without printing credential values. The active API's local settings reference Azure SQL and enable developer authentication. This is why existing smoke/seed scripts were not run. Local settings files are ignored by Git; their exclusion is not a substitute for historical secret scanning.

Sensitive assets include employee profiles, password hashes, roles/permissions, organization identifiers, project budgets/plans, supplier contacts/pricing, stock balances/valuation, purchase orders, uploaded files, audit records, and JWT signing material. The main boundaries are browser-to-API, identity-to-organization context, resource-to-parent references, API-to-SQL, API-to-Blob, and application-to-telemetry/outbox.

## Findings

### ERP-001: Credential-less Login for Accounts Without Password Hashes

- Severity/category: Critical, authentication bypass.
- Location: `backend/src/ERP.Application/Identity/AuthService.cs`, LoginAsync; POST /api/v1/auth/login.
- Evidence/reproduction: a synthetic active organization and user with PasswordHash=null were accepted with null, empty, and arbitrary supplied passwords. All three rejection regressions failed before the fix.
- Root cause: password verification ran only when a stored hash existed.
- Impact: knowledge of an active account identifier could obtain that account's JWT, including administrative roles.
- Implemented fix: require a nonempty stored hash, supplied password, and successful existing password verification. No password algorithm or provider was replaced.
- Verification: AuthenticationTests covers all three bypass cases and provisioned-account correct/wrong/missing-password behavior.
- Status/risk: code fixed. Accounts without passwords can no longer sign in. Securely provision authorized users before rollout; do not restore passwordless fallback. Existing JWTs are unaffected by this code change: approved revocation/signing-key rotation or expiry containment is a deployment prerequisite, not an action performed during this audit.

### ERP-002: Header Impersonation Allowed Outside Development

- Severity/category: High, configuration-dependent authentication/tenant impersonation.
- Location: `backend/src/ERP.Api/Security/CurrentUser.cs`, constructor.
- Evidence/reproduction: ERP_DevAuthEnabled=true plus attacker-supplied X-User-Id, X-Organization-Id, and X-Permissions authenticated synthetic requests in Production, Staging, and an unspecified environment. Three tests failed before the fix.
- Root cause: configuration opt-in had no environment fence.
- Impact: a hosted misconfiguration could allow forged organization and permission context without a JWT.
- Implemented fix: require both the explicit flag and AZURE_FUNCTIONS_ENVIRONMENT=Development. Validated principal claims continue to take precedence over headers.
- Verification: AuthorizationTests checks all denied environments, explicit development opt-in, spoofed tenant-header precedence, anonymous denial, and insufficient permission denial.
- Status/risk: regression verified. Production settings must still keep developer authentication disabled and must not advertise a Development environment. No deployed setting was inspected or changed.

### ERP-003: Inventory State Changes Did Not Check Original Status

- Severity/category: High, concurrency/integrity.
- Location: GoodsReceiptConfiguration and StockTransferConfiguration in `backend/src/ERP.Infrastructure/Persistence/Configurations/InventoryConfigurations.cs`; approval/rejection/dispatch/receive services.
- Evidence/reproduction: the SQL Server EF model did not mark Status as a concurrency token. Two model regressions failed before the fix. Independently loaded approval/rejection or duplicate dispatch requests could both pass application status checks; stock rowversion alone does not protect a reject path or an external-source dispatch.
- Root cause: a transaction protects atomicity, but ordinary read-committed transactions do not make an earlier application status check conditional at update time.
- Impact: conflicting document states, duplicate transitions, and inconsistent lifecycle/audit outcomes.
- Implemented fix: mark both existing Status properties as concurrency tokens. EF includes the original status in UPDATE predicates; the existing UnitOfWork translates conflicts to HTTP 409. No column or migration is needed.
- Verification: PersistenceModelTests passes for both mappings. SqlServerConcurrencyTests contains receipt approval/rejection, duplicate dispatch, and stock/ledger rollback tests.
- Status/risk: implemented and model-verified, **not database-race-verified**. LocalDB failed before test setup. These tests use EF-created disposable schema, so even a successful future run must be followed by checks against the deployed SQL-script schema and full service workflows. Status tokens do not protect unrelated same-status edits or supply request idempotency.

### ERP-004: Supplied Row Versions Did Not Prevent Stale Browser Writes

- Severity/category: High, lost updates/input error handling.
- Location: ProjectService.UpdateAsync, TaskService.UpdateAsync, ItemService.UpdateAsync, PurchaseOrderService.UpdateAsync.
- Evidence/reproduction: assigning client bytes to the entity's current RowVersion left EF's freshly loaded original concurrency value unchanged. Synthetic stale edits reached the write path; malformed base64 raised FormatException instead of a conflict.
- Root cause: client read-time version was not compared with the current record version.
- Impact: old forms could overwrite changes committed before the update request loaded the row; malformed tokens could cause HTTP 500.
- Implemented fix: compare the opaque supplied token with the loaded row's encoded version before mutation. Retain the loaded EF original version to catch writes occurring after that comparison.
- Verification: 16 StaleWriteTests cover stale, malformed, matching, and omitted tokens across all four services. Invalid versions leave fields unchanged.
- Status/risk: service regressions verified. Tokens remain optional to preserve API compatibility. Requests omitting them still lack read-to-submit stale-form protection; requiring tokens for every writer is unfinished contract/UI work. Live SQL simultaneous-write verification remains blocked.

### ERP-005: Duplicate Receipt Lines Could Over-Receive a Purchase Order

- Severity/category: High, procurement/financial integrity.
- Location: GoodsReceiptService.ApproveAsync/PostAsync in `backend/src/ERP.Application/Inventory/InventoryTransactionServices.cs`.
- Evidence/reproduction: two receipt lines of quantity 6 each were accepted against open quantity 10. A receipt of 8 against PO lines of 3 and 7 put all 8 on the first line. Both regressions failed before the fix.
- Root cause: each input line was checked against the same full remaining quantity, and posting selected only the first matching PO line.
- Impact: excess inventory/valuation and incorrect purchase-order quantities/status.
- Implemented fix: validate total received quantity per item and distribute posting across matching PO lines without exceeding any line's remaining quantity.
- Verification: GoodsReceiptTests verifies rejection before mutation and correct split allocation/status.
- Status/risk: synthetic service tests pass. Real concurrent approvals, repeated new receipt requests, UOM equivalence, and pre-existing inconsistent PO data still require database/workflow tests.

### ERP-006: Employee Department Assignment Was Not Tenant-Validated

- Severity/category: High, indirect organization isolation/integrity.
- Location: UserService.CreateAsync/UpdateAsync; `db/schema/erp-schema.sql` DepartmentId FK references only core.Departments(Id).
- Evidence/reproduction: create and update accepted department identifiers without checking organization membership. Both service rejection tests failed before the fix. A foreign existing ID would satisfy the single-column FK; a nonexistent ID would instead fail later in SQL.
- Root cause: scoped employee lookup did not validate the tenant of the submitted related object.
- Impact: cross-organization associations and corruption of department-based rules; no cross-organization data-read exploit was demonstrated.
- Implemented fix: inject the existing IDepartmentRepository and require ExistsAsync(currentOrganizationId, departmentId) before mutation.
- Verification: TenantIsolationTests verifies create/update rejection; existing foreign-role assignment and missing-document download tests also pass. The blob client is never opened for a document lookup rejected by the scoped repository.
- Status/risk: service-boundary verified with mocks; SQL-backed adversarial isolation across every endpoint is still pending. Existing inconsistent rows were not queried or repaired.

### ERP-007: Dependency Advisories

- Severity/category: Critical initial advisory maximum, vulnerable dependencies.
- Location: frontend manifests/lockfile; legacy root manifests/lockfile; .NET package references.
- Evidence/reproduction: initial frontend npm audit reported 14 advisories: 1 Critical, 7 High, 5 Moderate, 1 Low. The root TypeScript project separately reported 5: 3 High, 2 Moderate.
- Root cause: outdated direct and transitive dependencies; no tracked automated advisory gate existed at the initial review.
- Impact: advisory-specific risks include proxy trust/IP spoofing, parser/route denial of service, development-server file exposure, router redirects, and utility handling. Applicability differs: the Express server does not enable trust proxy and the SPA does not use SSR hydration, so advisory presence alone is not proof of exploitability.
- Implemented fix: Express 4.21.0 to 4.22.3, React Router DOM 6.26.2 to 6.30.6, Vite 5.4.8 to 5.4.21, plus compatible proxy-addr/source-map-js transitive updates. Lockfile updated; no forced ExcelJS downgrade or untested major upgrade.
- Verification: frontend production build and TypeScript check pass. The 2026-10-18 full frontend snapshot was 7 advisories (1 High, 6 Moderate); production-only was 4 Moderate. The fresh 2026-10-24 scan reports 9 (3 High, 6 Moderate), including 6 production-only findings (2 High, 4 Moderate). The new High findings involve Express/body-parser as well as the retained Vite finding; runtime findings must not be dismissed as development-only.
- Follow-up fix: a compatible legacy brace-expansion update moved versions 2.1.4 to 2.1.7 and 5.0.9 to 5.0.12. The fresh legacy scan dropped from 6 High to 5 High; its build passes. Direct dependency versions were preserved. Registry checks show latest Express 4.x at 4.22.3 and body-parser 1.x at 1.20.8, still within affected ranges. No forced major update or downgrade was applied.
- Status/risk: partially fixed; High findings remain release blockers. Do not expose affected development tooling to untrusted networks. The public NuGet cross-check again failed TLS negotiation on 2026-10-24; .NET advisory clearance remains unverified. CI now defines npm High/Critical gates and transitive NuGet auditing with audit failures treated as errors. The workflow has not run remotely; its npm gates are expected to fail until findings are remediated or formally reviewed through an explicit risk process, not suppressed automatically.
- Further investigation: a local Express 5.3.0 trial reproduced its incompatible bare-wildcard startup failure; a named wildcard then passed all 5 static-server HTTP cases. However, its installed body-parser dependency still matched the configured advisory feed's affected range below 2.4.0, so the major upgrade did not reduce findings and was backed out. Express remains pinned to 4.22.3; no forced fix, override, downgrade below the starting version, or audit exception was retained. The HTTP tests remain in place for a future real fix.
- Registry/source gate: configured-registry queries returned latest body-parser 1.x at 1.20.8, and Express 5.3.0 metadata required body-parser ^2.3.0; explicit public-registry queries returned latest body-parser 1.x at 1.20.5 and 2.x at 2.2.2. These differ from the configured feed's proposed patched ranges of 1.20.9/2.4.0. Reconcile approved package provenance, advisory sources and release availability before treating any automated upgrade suggestion or differing CI result as clearance. The discrepancy alone is not evidence of compromise. Reviewed server code mounts no body-parser middleware, but reachability review is not an automatic waiver of installed-dependency findings. Counts remain 9 frontend findings, including 3 High; production-only remains 6, including 2 High.

### ERP-008: Reference-Cache Miss Fan-Out and Unbounded Value Retention

- Severity/category: Medium, scalability/reliability.
- Location: `backend/src/ERP.Api/Common/ReferenceCache.cs`.
- Evidence/reproduction: 16 simultaneous same-tenant/key misses invoked the loader 16 times. The old dictionary only removed expired values during invalidation, so read-only traffic could retain expired entries.
- Root cause: check/load/set was not coalesced, and expiration was not managed by a bounded cache.
- Impact: redundant SQL work during cold starts/expiry, increased load/latency, retained cache values.
- Implemented fix: MemoryCache with absolute expiration and a 2048-entry size limit; per-versioned-tenant-key Lazy<Task> coalescing; completed/failed in-flight entries are removed. Singleton disposal releases the cache.
- Verification: ReferenceCacheTests measures 16 requests to 1 loader invocation after the fix and checks organization separation, failure retry, and invalidation during loading.
- Status/risk: measured unit-workload improvement, not an HTTP throughput benchmark. The limit counts entries, not bytes; organization/group version metadata and in-flight key cardinality are not byte-bounded. Cache invalidation is process-local, not distributed across Function instances. Loader cancellation is shared by callers of the same in-flight key.

### ERP-009: Session Lifecycle Needed Current-State Enforcement

- Severity/category: High, session/authorization lifecycle.
- Location: JwtAuthenticationMiddleware, JwtTokenService.Validate, CurrentUser, UserService, frontend AuthContext.logout, UserRepository.GetRoleNamesAsync/GetPermissionCodesAsync.
- Evidence/reproduction: previously JWT validation checked signatures and expiry without current user/organization status, password version, or memberships. Permissions/roles came only from embedded claims. Browser logout only clears local storage. Role-name/permission queries did not consistently exclude inactive roles.
- Root cause: no server-side token/session version, revocation lookup, or live membership validation.
- Impact: a stolen or previously privileged token can remain usable until expiration, including after a user is disabled or changes a password. An inactive role can still contribute newly issued claims.
- Implemented follow-up: login binds tokens to a SHA-256 fingerprint of the existing salted password hash (not the password/hash itself). Middleware resolves a request-scoped UserSessionValidator and checks the active organization, tenant-scoped active user, credential fingerprint, and exact current role/permission sets before endpoint execution. Role and permission queries now require active roles in the user's organization, active users, and active permissions. Missing credential-version claims and invalid Bearer tokens are rejected rather than falling through to developer authentication.
- Verification: 14 synthetic policy cases cover active/disabled/missing users and organizations, password replacement/clearing, changed roles/permissions, legacy tokens, foreign users, invalid IDs, and anonymous principals. Five middleware cases verify valid, revoked, invalid-token, unavailable-store, and anonymous paths, including that rejected requests never reach the endpoint. Existing login/JWT tests additionally verify credential-version issuance and round-trip preservation. All 39 identity tests pass; these are database-free tests, not live SQL role-filter evidence.
- Status/risk: partially remediated. Checks happen on every authenticated request without a process-local authorization cache; storage errors fail closed. They add up to four sequential database reads per authenticated request, which requires staging measurement. Account/authorization changes committed before a new check are observed by that check; already-running requests are not cancelled. Permanent revocation still needs a persisted session/security version: restoring an old account/role state can otherwise make a still-unexpired token usable again. Browser logout still does not revoke a stolen token. SQL-backed filtering tests and scaled-out verification remain required.
- Rollout: all pre-change tokens lack credentialVersion and will be rejected by upgraded instances. Require users to sign in again and drain/replace old instances; mixed old/new deployments do not enforce the policy uniformly. No signing key was rotated and no database migration was introduced.

### ERP-010: No Application-Level Login Throttling or Lockout

- Severity/category: High, authentication abuse/resource exhaustion.
- Location: AuthFunctions.Login, AuthService, password verification path.
- Evidence/reproduction: login directly validates/looks up/verifies/issues. Repository source search found no rate limiter, 429, lockout, token version, or revocation implementation. No live brute-force test was performed.
- Root cause: absent application anti-automation policy; deployed gateway protections are unknown.
- Impact: credential guessing, account discovery via timing differences, and CPU/database exhaustion during repeated attempts.
- Recommended fix: enforce a distributed, tenant/account-aware throttle with safe network identity handling and monitoring; test across scaled-out instances. Do not rely on a singleton in-memory counter for production limits.
- Verification/status: application control gap confirmed; perimeter exploitability unverified and unresolved. Run bounded synthetic 429/recovery and enumeration tests only in isolation.

### ERP-011: Purchase-Order Related IDs Were Not Consistently Scoped

- Severity/category: High, indirect tenant isolation.
- Location: PurchaseOrderService.CreateAsync/UpdateAsync in ProcurementServices.cs.
- Evidence/reproduction: ProjectId was assigned from both requests without a project membership lookup. Update also assigned WarehouseId without the create path's warehouse organization check, and optional line UomId was not tenant-checked in either path. Five negative regression cases failed before the fix; the existing create-warehouse rejection and two valid-reference cases already passed. The top-level PO lookup does not validate supplied related IDs.
- Root cause: incomplete reference validation across create/update paths.
- Impact: cross-organization associations; potential downstream disclosure depends on consumers/joins and has not been demonstrated.
- Implemented fix: share one reference-validation method across create and update; validate project, warehouse, optional line UOM, item, and supplier using server-derived organization context and the existing repositories, before mutation or saving.
- Verification: eight TenantIsolationTests cases cover foreign project/warehouse/UOM IDs on both paths and valid local references. All pass, alongside the 16 stale-write cases. No database migration or public HTTP contract change is required.
- Status/risk: service-boundary fixed with synthetic repositories. SQL-backed negative tests, other procurement entry points, existing inconsistent data, and downstream consumers still need review before claiming complete procurement isolation. The added checks introduce per-line reference queries; bulk optimization must retain all tenant predicates.

### ERP-012: Transaction Retry Delegates May Replay Mutable Tracked State

- Severity/category: Medium, suspected retry/data integrity issue.
- Location: UnitOfWork.ExecuteInTransactionAsync, EnableRetryOnFailure registration, and delegates that append lines/events or mutate tracked entities.
- Evidence: execution strategy can rerun an action using the same scoped DbContext and already-mutated aggregates after transient errors. Several services construct/mutate aggregates outside and inside the delegate. No fault injection or ambiguous-commit reproduction was possible.
- Potential impact: missing reissued commands, duplicated in-memory children/events, or ambiguous transaction outcomes.
- Recommendation/test: inject failures before/after SaveChanges and commit against disposable SQL Server; determine safe transaction rehydration/idempotency per workflow. Do not globally disable retries or increase isolation to conceal the risk.
- Status: suspected, not a confirmed reproduced corruption defect; unresolved pending evidence.

### ERP-013: Legacy Database Diagnostics Exposed Internal Details

- Severity/category: Medium, information disclosure.
- Location: `src/functions/dbTest.ts`, dbTest.
- Evidence/reproduction: success returned database/login identity, failures returned raw error text, and request logging included the full URL, potentially including a Functions key in its query string. Six regression cases failed before the fix; the existing function-key registration assertion passed. No live database or diagnostic call was made.
- Root cause: unnecessary metadata selection plus unsanitized response/log formatting.
- Impact: internal server/identity/error details could reach diagnostic callers; query-string access keys could reach application logs.
- Implemented fix: probe with SELECT 1 AS connected, return only connected=true on success, retain HTTP 500 with a fixed error message and invocation traceId on failure, and log only fixed messages. Do not log request URLs or raw exception values. Existing function-key registration, GET method and route are unchanged. The intentionally removed success info field is a diagnostic response-contract change; diagnostic consumers must not rely on database/login metadata.
- Verification/status: all 7 Node built-in tests pass: registration, successful query/response, request-log sanitation, and Error/string failures at both connection and query stages. getPool is mocked throughout; no remote connection is attempted. Root npm test now builds and runs this suite, and CI invokes it. Runtime key enforcement, administrative network exposure, legacy pooling/token refresh, and protected telemetry access still require deployment review; these mocked tests do not prove those controls.

### ERP-014: Legacy TypeScript Build Included Frontend Sources

- Severity/category: Medium, build/release reliability.
- Location: root tsconfig.json, npm run build.
- Evidence/reproduction: the release-build check failed with frontend JSX errors. With no include boundary, the root TypeScript project discovered unrelated frontend files despite using CommonJS and no JSX configuration.
- Root cause/impact: the separate legacy service and frontend did not have isolated compiler inputs, so the legacy release build failed and could emit unintended frontend artifacts.
- Implemented fix: add include for src/**/*.ts while preserving rootDir and dist/src output paths used by the Functions manifest.
- Verification/status: the exact failing npm run build now passes. The CI matrix builds the two projects separately. Existing ignored build outputs were not deleted.
